# Roadmap: Secure WebRTC Video Conferencing over IP

Goal: build a video conferencing app with WebRTC, our own signaling server
(custom WebSocket API), RTP media transport, security (authentication +
encryption), and QoS monitoring with congestion detection.

Each phase ends with something you can **run and see working**. We do not move
on until the current phase works and you understand why.

## Tech choices

| Part | Choice | Why |
|---|---|---|
| Signaling server | Node.js + Express + `ws` (WebSocket) | Small, readable, the "custom API" option from the brief |
| Client | Plain HTML + JavaScript (no framework) | Keeps focus on WebRTC APIs, nothing hidden by a framework |
| Media transport | WebRTC (RTP/RTCP over SRTP, built into the browser) | Required by the brief |
| NAT traversal | Public STUN, then our own TURN (coturn in Docker) | Calls must work across networks |
| Security | HTTPS/WSS, JWT login, DTLS-SRTP | Auth + encrypted signaling + encrypted media |
| QoS | `RTCPeerConnection.getStats()` + `RTCRtpSender.setParameters()` | Measure, detect congestion, adapt |

SIP (JsSIP + Asterisk) is the alternative signaling path. We document it as a
comparison in the report, but the custom API is what we build.

## Phase 0: Project setup ✅
- Git repo, README, this roadmap.

## Phase 1: Local media (camera and microphone) ✅
- `getUserMedia()`: ask for camera/mic, show the local video in the page.
- Understand: media streams, tracks, permissions, why browsers need HTTPS
  (or localhost) for this.
- **Done when:** opening the page shows your own camera.

## Phase 2: Signaling server ✅
- Node.js server serving the client and a WebSocket endpoint.
- Rooms: `join`, `leave`, list of peers in a room.
- Message relay: `offer`, `answer`, `ice-candidate` forwarded to the target peer.
- Understand: why WebRTC needs signaling but does not define it.
- **Done when:** two browser tabs join the same room and see each other's join
  messages in the console.

## Phase 3: First 1-to-1 call ✅
- `RTCPeerConnection`, SDP offer/answer exchange through our server.
- ICE candidates, public STUN server.
- Show the remote video.
- Understand: SDP (codecs, media lines), ICE candidates (host, srflx, relay),
  where RTP starts flowing.
- **Done when:** two tabs (then two machines on the same LAN) see and hear each
  other.

## Phase 4: NAT traversal with TURN ✅
- Run coturn in Docker, with credentials.
- Configure the client with our STUN/TURN servers.
- Force relay mode to prove TURN works.
- **Done when:** a call works with `iceTransportPolicy: "relay"`.

## Phase 5: Security ✅
- HTTPS + WSS with a local certificate (mkcert).
- Login endpoint issuing a JWT; the WebSocket refuses connections without a
  valid token; a user can only send messages inside rooms they joined.
- Validate every signaling message (type, size, fields). Basic rate limiting.
- Short-lived TURN credentials generated by the server (not hardcoded).
- Verify media encryption: DTLS-SRTP fingerprints in the SDP,
  `chrome://webrtc-internals`, and a Wireshark capture showing RTP payloads are
  encrypted.
- **Done when:** unauthenticated clients are rejected and the capture shows
  SRTP only.

## Phase 6: Multi-party calls ✅
- Mesh topology: each participant connects to every other (up to ~4 people).
- Handle join/leave mid-call, grid layout.
- Understand: why mesh does not scale and what an SFU does (documented, not
  built).
- **Done when:** 3 participants talk in one room.

## Phase 7: QoS monitoring ✅
- Poll `getStats()` every second per connection.
- Compute: RTT, jitter, packet loss %, bitrate in/out, frame rate, resolution.
- Show a live stats panel per participant.
- Understand: RTCP reports and where each metric comes from.
- **Done when:** the panel shows live numbers that react when the network changes.

## Phase 8: Congestion detection and adaptation ✅
- Define thresholds (example: loss > 5%, RTT > 300 ms, jitter > 30 ms).
- Simple state machine: `good -> degraded -> congested` with hysteresis so it
  does not flap.
- On congestion: lower max bitrate / resolution with `setParameters()`;
  restore gradually when the network recovers. Show the state in the UI.
- Test with `tc netem` (add delay, loss, bandwidth limit) on Linux.
- **Done when:** adding 10% loss with netem makes the app detect it, reduce
  bitrate, and recover after the loss is removed.

## Phase 9: Features and polish ✅
- Mute / camera off, screen sharing, text chat over a DataChannel, hang up.

## Phase 10: Packaging and report ✅
- `docker compose up` starts the server and TURN.
- Test scenarios with measurements (before/after adaptation).
- Report: architecture diagram, signaling sequence diagram, security analysis,
  QoS results, SIP vs custom API comparison.

## How each phase was verified

| Phase | Proof |
|---|---|
| 1-3 | `npm run e2e`: 3 headless Chrome users with fake cameras see each other |
| 4 | `RELAY=1 npm run e2e` with coturn: stats show `path relay` |
| 5 | `npm test`: forged tokens rejected, room isolation, hashed passwords, HMAC TURN credentials, headers; HTTPS/WSS checked with a self-signed cert; SDP carries a DTLS fingerprint |
| 6 | `npm run e2e`: 3 participants, hang up updates the others |
| 7 | Stats panel shows live RTT, loss, jitter, bitrate, resolution, fps, path |
| 8 | `npm run congestion`: 15% loss -> congested, video capped to 89 kbps, recovers to good |
| 9 | Chat checked in `npm run e2e` |
